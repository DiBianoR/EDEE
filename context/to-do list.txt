🌗Automate Firestore expiry (not urgent - nothing is expiring right now)
  - 2026-11-21: the bucket side is done. Every finished job writes {job_id}/job.json (the doc minus the
    transcript) and its doc's `ttl_expiry` is cut to 1 day; POST /archive does the same for a crashed or
    stalled run (the frontend calls it when its watchdog gives up); /summary, /restore and the frontend read
    an expired job back from the bucket. `ttl_expiry` is a real datetime (Firestore Timestamp), set by the
    frontend at start (7 days) and the state manager at the end (1 day).
  - LEFT TO DO: (1) one-off backfill: POST /archive/{job_id} for every job_states doc, so docs that exist only
    in Firestore (crashed runs, anything from before job.json) get their bucket copy; (2) then enable a
    Firestore TTL policy on job_states.ttl_expiry. Older docs already carry a ttl_expiry from the frontend,
    mostly in the past, so the policy will delete them soon after it is switched on: do (1) first.
  - (1) is written: `py -3 firestore_backfill.py` (dry run), then `--go`, AFTER the push deploys /archive
    (the script checks and refuses otherwise). Skips unfinished jobs updated in the last 24h; rerunnable.
    Needs `pip install google-cloud-firestore google-cloud-storage` locally.
  - Note: with Firestore scrubbed, the bucket is the only record, and its lifecycle rule deletes after 360 days.
  - TTL is currently OFF; bucket lifetime extended to 360 days, and the Google Sheet
    tracks failed runs, so no data is at risk today
  - TTL needs a real Firestore Timestamp field. Our `timestamp` is an ISO *string*
    (state manager writes datetime.now(timezone.utc).isoformat()), so a TTL policy on it
    would silently delete nothing. Would need a new `expire_at` written as a datetime
    object, not .isoformat()
  - A TTL policy does apply to existing docs, but only ones that already carry the field,
    so anything already written would need a one-off backfill
  - Alternative to raw TTL: scheduled archive-then-delete sweep (Cloud Scheduler -> Cloud
    Run, reusing POST /archive-incremental/{job_id}), so nothing gets deleted that wasn't
    archived first. TTL is a blind deleter; a sweep can enforce the ordering
