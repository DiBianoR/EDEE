# EDEE-main: structure map

Read this before tracing the Main Workflow (n8n name **EDEE-main**, id `HtwI6u1ae2xwKw1f`). Every node also carries a one-line **note** ("road sign"):

```
<SECTION> · <what it is>. <context> | in: … | out: [branch]target, …
```

The section names below match the notes. Notes are generated by `main_workflow_nodes/build_node_notes.py` (wiring read from the live graph, context hand-written) and pushed with `py -3 n8n_notes.py apply`. When you change the graph, re-run backup → build → apply so the signs stay true.

Snapshot this map describes: 2026-11-05, published `d1cf8d70` (Resume final review, incl. redrawing the base diagram); Load Config `44499a51`. There are 265 nodes: 205 in the pipeline (191 + 14 resume nodes), 38 detached (templates and junk), and 22 sticky notes.

## The three conventions that explain most of the canvas

1. **cfg → agent pairs.** Almost every step is a Set node named `cfgN` that sets `PHASE_ID` / `AGENT_ID` / `TASK_ID` (plus any extras such as an image or a retry counter). It is followed by an Execute Workflow node named `<agent> - <task>` that calls the **Universal Agent Sub-Workflow**. The cfg number says nothing about order; it is creation order. The prompt, the schema and the model all come from `config.js` keyed by that task. So to understand a step, read the task in `config.js`, not the node.
2. **The envelope.** Between steps the item is `{config, session_state, session_events}`. Each `Phase N - Output` Set node strips the item back to exactly that, and each `Load Phase N Config` passes it through (config is only *built* once, at `Load Phase 1 Config`). Anything else at the top level of an item (an image, `python_code`, `human_message`) is single-hop. Universal Agent Node 1 sweeps stray top-level fields into `session_state`, so never put big or temporary data at the top level of an agent call.
3. **Reach-backs by name.** Some expressions read other nodes directly: `$('Prepare for Vision')` (the scaffold image, in cfg25/cfg26), `$('artist - render_final')` (the illustration, in cfg27–30, cfg62 and Send Final Broadcast), and `$('cfg16')`, `$('cfg18')`, `$('cfg25')`, `$('cfg63')`, `$('Hoist python_code')` (retry counters in the loop switches). Renaming those nodes, or entering the graph somewhere they never ran, breaks these silently.

## Canvas layout

The sticky-note frames mark the phases from left to right: P1 x −4640…−2848, P2 −2752…−736, P3 −640…2848, P4 2944…3936, P5 4032…5216, P6 5312+. The two human gates sit **above** their phases (y < 1000). Detached templates are bottom-left (x −4600…−3000, y 3100…4400).

## Flow by section

**ENTRY.** There are three triggers, and they converge on `Set API Key` → `Load Phase 1 Config`:
- `API Trigger`: the frontend webhook. `/webhook` runs the published version; `/webhook-test` runs the draft.
- `When Executed by Another Workflow`: the Test Orchestrator. It sends no `human_review_mode`, so batch runs are automatic.
- `When clicking ‘Execute workflow’` → `Select Query` → `Mock Input1`: manual runs from the query library, which bypass `Set Job`.

**P1 VALIDATION.** `extract_math_and_visual` → `Logic Router` (Code) sets `validation_route` → `Problem Validation Agent - Switch`. Its outputs: `both` (ready) → `check_conflict` → `valid`; `problem` (math only) → `propose_diagram`; `visual_only`; `neither` → failure. The three format_* tasks converge on `Problem Validation Agent - Output`.

**P2 SPECIALISTS → SITUATIONAL → MERGE+REVIEW LOOP.**
- The five specialists run in a fixed sequence: dimension, layout, visual director, markup, educator.
- `situational_planning` sets flags that drive a chain of four IFs (3D, graphs, arrangement, artistic). Each IF either runs its specialist or falls through to the next.
- `merge_plans` → `cfg16` (counter) → `review_description` → `If Ready for code`: True → Phase 2 - Output; False → `retry_count` → cfg16; 3× → failure.

**P3 ROUTE+DESIGN.** `selector.choose_path` → `Route Workflow3`:
- STANDARD and COMPOSITE_PRIMITIVES (currently the same path) → `cfg inject constraints` (Code) → `inject_constraints` (no_model) → `design_scaffolding` → coding loop.
- DIRECT_IMAGE_GEN skips straight to `Archive Scaffolding`.

**P3 CODING LOOP / EXECUTION / VISION QA.** The loop head is **cfg18**, with five entries; it increments `coding_retry_count`. The three loops each have their own counter:

| Loop | Path | Counter (checked at) | Fail exit |
|---|---|---|---|
| Code review | plan_logic → write_code → syntax/logic/math reviewers → consolidate_review → `if bool_var3` → (False) troubleshoot → retry_count3 → cfg18 | coding_retry_count (`$('cfg18')`) | cfg54 |
| Execution | `Hoist python_code` → `Python Execution Node` (error output) → cfg57 → log_error → `if bool_var4` → troubleshoot1 → retry_count4 → cfg18 | execution_retry_count (`$('Hoist python_code')`) | cfg58 |
| Vision inspection | `Prepare for Vision` → 4 inspectors → consolidate_inspection → `inspections passed?` → (False) troubleshoot_visual → retry_count2 → cfg18 | inspection_retry_count (`$('cfg63')`) | cfg53 |

`Prepare for Vision` also broadcasts the render to `{job_id}/latest.png`. That broadcast is what the scaffold gate shows the human.

**P3 SCAFFOLD GATE (human)** and **P5 FINAL GATE (human).** These are documented in `main_workflow_nodes/README.md` (§1–7 for the scaffold gate, §8 for the final gate); the Code nodes' source is in that folder. Entry: `inspections passed?` / `if final_pass` → `Human review?` / `Final review?` (on True) or `Human available?` / `Final available?` (on MaxRetries). Exits: continue → `Archive Scaffolding` / `Phase 5 - Output`; rework → reset retries → cfg18 / cfg25; fail → cfg53 / cfg61; abort → report_error7 / 8.

**P3 EXIT.** `Archive Scaffolding` has three entries and pins `{job_id}/scaffolding.png`.

**P4 PRODUCTS → ARTIST.**
- The optional product-planning branch (config `customizable_products_in_phase4`, then the planner flag) leads into **cfg25**, the artist loop head, which has four entries.
- `plan_finishing` → `cfg26` → `render_final` → `Render OK?`: no image → retry up to 3×, then `cfg render abort`.

**P5 REVIEW LOOP.** Four verifiers (bias, aesthetics, safety, math) → `aggregate_feedback` → `if final_pass`: True → final gate or skip; False → troubleshoot_visual → retry_count5 → cfg25; 3× (counted at `$('cfg25')`) → rescue gate or cfg61.

**P5 RESUME (finished job → final gate).** A second entry point, above the final gate (x 3088…3904, y 384), plus two checks after `After final log`. It reopens a finished job so the human can do another correction round with the Final Gatekeeper. The Code sources are `main_workflow_nodes/resume_*.js`, and `patch_resume_final_gate.py` (re-runnable) applies them.
- **Entry:** the frontend's "Resume final review" posts to `resume-final-gate` with `{source_job_id, mode: overwrite|new, target_job_id, max_text_tier, max_image_tier, style_preference}`.
  - `Resume: Load Job` refuses jobs that are busy or have nothing to review, loads the transcript (`/transcript`) and works out the style. That's exact for runs that finished after 2026-11-04: Load Config puts `style_preference` in the config, and Send Final Broadcast / Resume: Restore Completed append a `run_settings` event recording it, plus the tiers. The author is in no agent's history_scope, the frontend hides it from the log, and it stays in the ZIP. For older jobs the style is inferred from a phrase of each style description in the artist's logged prompts; those jobs can only have used the five original styles. It works for any job with a transcript and a final image.
  - Then `Resume: Respond OK` → `Set API Key (resume)` → `Load Resume Config` (fresh config, `human_review_mode` "wait").
  - `Resume: Rebuild State` replays the transcript into session_state. In overwrite mode it first calls `/backup-round`, which copies the result to `{job}/previous/<UTC>/`, and refuses to continue without it. In new mode it copies the transcript and scaffold to the new job. It posts a `final_gate` / `resume_final_gate` marker event and enters `Final Gate: Announce` as a fresh gate.
- **Inside the gate,** everything runs as usual, with three resume-aware spots:
  - `cfg25` / `cfg26` take the scaffold from `Resume: Rebuild State` when `Prepare for Vision` never ran.
  - `cfg final review` counts final_review turns only after the last marker, so the first message is `_open` again.
  - The frontend's conversation panel also starts at the marker.
- **Exits:**
  - `Resume: keep previous? (continue)`: resumed and the artist never ran (approved unchanged, walked away, or the Gatekeeper found nothing to change) → `Resume: Restore Completed`. That marks the job completed with its previous image, message and report: no Phase 6, no model calls.
  - `Resume: keep previous? (abort)`: a stop in a resumed job also keeps the previous result.
  - A repaint follows the normal path to Phase 6 and Send Final Broadcast.
  - A failure (for example, rejected 3× with nobody answering) marks the job failed, honestly; in overwrite mode the previous result is in `previous/`.

**P5 RESUME: REDRAW BASE DIAGRAM (resumed jobs only).** In a resumed job the Final Gatekeeper runs `final_review_open_resume` / `final_review_reply_resume`: the normal prompts with the "geometry is fixed" rule replaced by "the base diagram can be redrawn; explain what that involves and get an explicit yes". `config.js` derives these from the originals and throws if the replaced sentences move. Their schema adds `redraw_scaffold` and `scaffold_changes` (geometry only; painting stays in `fix_instructions`). A confirmed redraw leaves the gate as `rework`.
- **Routing:** `Resume: redraw scaffold?` sends it to `Resume: Prepare Redraw` → `cfg amend description` → `image_detail_planner - amend_description` → `Route Workflow3`, which is the normal Phase 3 from the job's original route: design_scaffolding (new blueprint) → coding → inspection → **scaffold gate** → Archive Scaffolding → Phase 4 → Phase 5 → final gate.
- **Prepare Redraw** restores the description Phase 3 used: the last `latest_description` written by `image_detail_planner`, so Phase 4's product-decorated version never reaches Phase 3. That works on any job, from its transcript. It also clears stale gate flags, arms the painting directives, and posts a `human_gate` / `scaffold_redo` marker that the coding team sees and that `cfg human review` counts from.
- **Why this is a clean first pass:** Phase 3 has never run in a resumed execution, so no node runs twice and nothing can pick up a stale earlier run.
- **Stopping:** a stop at the redo's scaffold gate goes through `Resume: keep previous? (scaffold abort)` to `Resume: Restore Completed`, which keeps the previous result.
- **Normal runs** never reach any of this: every check requires `Resume: Rebuild State` to have run, and both edited task-picking expressions return their old values when there's no marker.

**P6 REPORT.** `generate_user_message` → `generate_archival_report` → `Phase 6 - Output` → `Send Final Broadcast`, the completion payload; if it fails, the run fails.

**Failure exits.** Every `error_handler - report_error*` / `report_unknown_error*` node is a terminal no-output call (the task has `terminal_mode: failed`). Its cfg sets `error` (MaxRetriesExceeded, UserAborted or RenderFailed), and the error_handler agent explains it to the user.

## Detached nodes: never part of a run

**Templates.** These are copy-paste "machines" to build new circuits from. They have blank `PHASE/AGENT/TASK` fields and placeholder values:

| Template | Nodes |
|---|---|
| basic agent call | cfg → universal agent |
| agent-driven IF | cfg49 → T/F agent → if bool_var1 (on `session_state.bool_var`) |
| agent IF with retry loop | cfg45 (counter) → T/F RETRY agent → if bool_var → False: cfg35 → error_expert.troubleshoot → retry_count1 → cfg45; MaxRetries: cfg46 → report_error1; True left open |
| agent-driven SWITCH | cfg50 → CASE(enum) agent → Route Workflow (enum_var) |
| agent picks next task | cfg51 → CASE(enum) agent1 → task picker (enum→TASK_ID map) → chosen task |
| enum→task lookup | task picker1 → chosen task1 |
| code-computed next task | complex conditional → chosen task2 |
| error exits | cfg47 → report_error; cfg48 → report_unknown_error |

**Legacy / unused:**
- `cfg1`/`cfg2` + extract_math / extract_visual: the old two-call Phase 1.
- `cfg36` + detect_error_loops + `If in error loop`: never wired in; the IF has an empty condition.
- `Mock Input`: the old fixed payload.
- `TODO: Primitives`: a placeholder for a separate COMPOSITE_PRIMITIVES path.

**Debug tool:** `View Image` turns `base64_img_string` into a binary you can view.

## Fixed 2026-11-04 (published as `e5a0b4c0`)

1. **Typing never extended a review gate.** Both Resolve nodes emit `human_action: "extend"` when the typing beacon pushed the gate's deadline past the current wait slice. `Human decision` / `Final decision` had no rule for it: output 1 tested `corrections` only, and with no fallback output the item was dropped and the run ended at the gate. This is why the "30 s to react" mode was disabled in the frontend (`REVIEW_MODES` in `ritel-frontend/app.py`). Output 1 is now `extend`, matching `extend` OR `corrections`, → Announce. The state manager's `/human-activity` was already deployed.
2. **`If Ready for code`**: the MaxRetries/False rules tested `ready_for_code`, which no agent outputs; they now test `ready_for_artist`, matching the True rule.
3. **`if bool_var3`**: the MaxRetries/False rules read top-level `$json.passed_review` (always undefined); they now read `session_state.passed_review`.

Items 2 and 3 never misrouted: the switch takes the first matching rule, and the True rule was right. They only made the switch fragile.
